# План имплементации Rendezvous MVP

Этот каталог превращает [SPEC](../spec/SPEC.md) в последовательность проверяемых этапов. Исходная спецификация остаётся источником продуктовых требований; файлы этапов определяют порядок реализации и критерии готовности.

Каждый файл — не только список фич, а техническое задание на этап: целевая структура модулей, ключевые контракты, алгоритмы и правила хранения, последовательность реализации, проверки и exit criteria. Имена файлов и snippets задают рекомендуемую архитектуру; при осознанном отклонении решение фиксируется ADR и сохраняет описанные границы ответственности.

## Правила выполнения

- Этап начинается только после выполнения его входных условий.
- Этап завершён только когда выполнены все пункты `Критерий выхода`.
- Hard constraints, scoring и ranking реализуются детерминированным TypeScript-кодом. LLM не участвует в вычислениях.
- Postgres хранит canonical application state. Mastra только оркестрирует вычислительный pipeline.
- Raw-ответы Tutu MCP не выходят за границу adapter/normalizer.
- Изменение revision, влияющее на travel, запускает новый workflow; устаревший результат не сохраняется.
- Приватные ограничения участника не попадают в group DTO, SSE events, логи и LLM prompts.

## Контрольные вехи

1. После этапа 04 ядро умеет ранжировать города в изоляции.
2. После этапа 07 несколько Telegram-пользователей видят живой пересчёт.
3. После этапа 08 закрыты все обязательные продуктовые действия.
4. Этапы 09–10 доводят MVP до устойчивого публичного демо.

## Как брать этап в работу

1. Проверить зависимости и открытые «точки решения» в файле этапа.
2. Зафиксировать неизвестные provider/deployment contracts коротким ADR до написания зависимого кода.
3. Реализовывать в порядке секции `Последовательность реализации` маленькими вертикальными изменениями.
4. Добавлять тест одновременно с модулем, а не отдельной финальной фазой.
5. Приложить к завершённому этапу evidence: команды проверок, migration/contract outputs и ссылку на рабочий сценарий.
6. Не переходить дальше при невыполненном `Критерии выхода`, кроме явно параллельных веток из таблицы зависимостей.

## Scope

`MUST` из SPEC входит в этапы 01–08. `SHOULD` сосредоточен в этапе 09 и выполняется в порядке: counterfactuals → template Why → compare → natural-language parser/free-form AI → дополнительная анимация. При дефиците времени сокращения выполняются строго по разделу 56 SPEC; live collaboration, Tutu MCP, fairness, ranking и visual explanation не сокращаются.
